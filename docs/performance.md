# 性能

## 参数提交

2026-10-22 的优化针对配套 Mod 的 GI pass 准备阶段。私有 GPU 程序在资源实例创建时链接，采样器槽位、体积尺寸及阴影图布局在该实例内保持不变，因此这些 uniform 改为链接后初始化一次。每次绘制继续绑定当前读写纹理，光源数量在注入阶段实时更新，光源位置、日月颜色、反弹和传播调度沿用原流程。改变体积或阴影尺寸时，已有资源重建流程会创建新程序并重新初始化。

原来每次 pass 会重复提交约 14–15 个固定或无效 uniform，并拼接采样器名称字符串。原生探针直接调用生产 `setup()`，核对四个程序的 26 个有效固定参数，预热后采样五组、每组 512 次 pass 准备。测试在帧率采样结束后运行，使用同一组反射调用参数，不包含绘制和 GPU 求解，因此结果表示 CPU 提交开销。

`shaders/` 的 235 个输入和配套 Mod 的 11 个 GPU 源文件均与本轮基线逐字节相同。生产网格 CRC、玻璃前方水面、水下玻璃、封闭房间和动态遮挡完成原生检查。原始记录保存在 `.preview/state-optimization/`。

| 单次 GI pass 准备 | 优化前 | 最终实现 |
| --- | ---: | ---: |
| CPU 同步耗时 | 约 0.95–1.09 µs | 约 0.55 µs |
| Java 线程临时分配 | 752 字节 | 8 字节 |

该表包含反射调用生产方法的固定开销，不包含绘制或 GPU 计算，不能换算为整机帧率。原生移动路线的原版三次平均为 19.26、18.78、16.71 FPS，最终实现为 16.28 FPS；每组均使用 120 FPS 上限、64 光源和 40³ GI 体积，未触发限帧。末尾原版也明显低于开头，且运行期间机器热状态由 nominal 变为 fair，本轮无法确认整机帧率改善。

26 个有效固定 uniform 的实际值全部通过校验。动态遮挡新增、移除与近处新光源映射检查通过，新光源约 0.56 秒获得映射。最终 JAR 相比基线只改变 `GpuLighting.class`，其余条目相同。原生截图未冻结波浪、云和粒子动画，因此不把独立运行的像素差作为数值等价证明；计算规则是否改变由源码和参数校验确定。

本轮还试验过只保存三个绘制附件的状态，以及用栈缓冲代替临时直接缓冲。OpenGL 的全局混合开关和颜色掩码会影响所有绘制缓冲，缩减覆盖需要同时改为索引接口，见 [Khronos 颜色掩码说明](https://wikis.khronos.org/opengl/GLAPI/glColorMask)和[状态开关说明](https://wikis.khronos.org/opengl/GLAPI/glEnable)。这些试验没有显示稳定的整帧收益，最终恢复了原有状态保存和恢复方式。

本轮只需替换配套 Mod 并完整重启 Minecraft，F3 + R 不会重新加载 Java 类。公开 Release 尚未更新。

## 计算裁剪

2026-10-21 的优化只跳过对当前画面没有贡献的计算。地形日月直射的天空光权重在等级归一值不超过 0.60 时为零，此时不再查询 PCSS。接收面导数仍在分支前计算，避免室内外边界出现未定义导数；非零调试视图保留完整阴影。近景雾色权重或背景透射率为零时，跳过天空方向、角度映射及查表。

默认配置、非零贡献的 PCSS 样本、点光源阴影、GI、反射、水体和颜色模型沿用原值。本轮没有配套 Mod 改动。原先尝试的 GI 相邻格特化虽通过系数对照，原生移动场景却由旧版约 15.8–16.5 FPS 降至约 7.9 FPS，紧凑版本约 13.9 FPS，因此两版均已撤回；单独计算阶段的加速不能代替整帧验证。

```bash
python3 tools/check_work_scheduling.py \
  --baseline-shaders /path/to/previous/shaders
```

工具展开生产 GLSL，在本机 GPU 上对照近景、远景、混合雾距、天气遮挡、室内、室内外光照过渡、石英材质与阴影调试视图。八组用例的最终 RGBA16F 输出最大差异均为 0。原始结果保存于 `.preview/fog-optimization/verification.json`。

1280×720 探针中，室内光照计算由约 1.742 ms 降至 0.742 ms，混合光照约 1.428→0.912 ms，石英材质约 2.170→1.805 ms。雾色修正的收益较小，近景约 0.643→0.627 ms，远景约 0.610→0.617 ms，与小幅分支成本和运行波动处于相近量级。由于本机 OpenGL 时间查询返回 0，以上使用同一上下文交替执行、显式等待 GPU 完成的同步耗时，包含驱动提交和等待开销，不等同于 GPU 时间戳或整机帧率。

原生客户端使用相同的 960×540 逻辑窗口、六区块视距、120 FPS 上限、64 光源和 40³ GI 体积走同一条路线。旧版两次平均为 16.46、15.79 FPS，最终版为 16.12 FPS，均没有触发限帧，因此本轮未确认整机帧率有显著提升。封闭石英房间和混合玻璃固定镜头的平均 RGB 差异约 0.35 个 8 位色阶，99% 的通道差异不超过一个色阶；该记录包含抖动、火焰及独立运行时的光照更新差异。截图、配置和逐帧计数摘要保存在 `.preview/fog-optimization/native/`。

## 修改范围

当前优化针对探索、走动和转动视角时，配套 Mod 重复采集遮挡、生成网格及提交更新造成的 CPU 和临时内存开销。光照模型、默认配置、阴影分辨率、光源数量、GI 体积、反弹次数和传播步数保持原值。

- 调度使用 Forge 的真实渲染帧事件，每帧更新一次，移除固定 16 毫秒轮询与主线程任务投递。
- 周期遮挡检查分片读取区块方块状态，未变化的光源复用已发布阴影。相机移动引起的快照边缘变化先验证再决定是否重建；近处放置、拆除方块继续优先刷新。
- 网格先统计外露面，再分配精确长度的顶点数组，避免为实体内部的不可见面分配大数组并复制。顶点顺序、位置和属性保持一致。
- RGB 体积的间接索引未变时跳过重复上传；同一纹理的内容更新不再触发所有外部 Shader 程序重绑。体积原点或有效性变化仍会刷新 uniform。
- 普通快照只记录完整方块的占用，发布场景时才按原有顺序展开几何；地图颜色的字节到线性空间转换预计算一次。部分方块继续读取实际形状。
- 地形雾和光照元数据内容相同时跳过纹理上传；完整地形更新一次提交当前原点与渐入参数。

普通场景快照和后台遮挡验证分别在约 2 毫秒的 CPU 软预算下分片推进。新增光源、近处编辑、玻璃接收缓存和 GI 继续使用已有更新数量。软预算不限制完整一帧的耗时，也不能限制单次 GPU 命令的执行时间。

## 检查方法

先构建配套 Mod，再运行生产网格检查：

```bash
python3 tools/build_companion.py --java-home /path/to/jdk
python3 tools/check_companion_performance.py --java-home /path/to/jdk
```

四组固定几何包含实心内部、孔洞及台阶。检查直接调用生产 Java 网格生成器，核对优化前记录的完整顶点字节 CRC 和长度，并测量预热后的每次分配。输出位于 `.preview/performance-verification/verification.json`；微基准耗时受 JIT 和系统负载影响。

原生客户端检查使用隔离的存档副本：

```bash
python3 tools/preview.py capture --native-only --refresh \
  --companion-jar /path/to/companion.jar \
  --shader-dir /path/to/frozen/shaders \
  --instance /path/to/game-instance --world 'World Name' \
  --scene perf_static --scene perf_walk --scene perf_edits \
  --scene reflect_corner --scene reflect_portal
```

`--companion-jar` 可分别提供旧版和优化版。每次完成后保存 `.preview/game/screenshots/`，再用以下命令比较；正式游戏目录的光影选项不受捕获助手修改。

```bash
python3 tools/check_companion_performance.py --java-home /path/to/jdk \
  --baseline-dir /path/to/baseline --optimized-dir /path/to/optimized
```

`perf_static` 和 `perf_walk` 分别记录静止与移动镜头。两版固定 64 光源、40³ GI 体积、4 次反弹、每次 12 步传播及每帧最多 8 步 GI 工作，其余画面设置使用相同 Shader 源码。客户端在预热 12 秒后统计渲染线程分配与 CPU 时间，捕获上限为 10 FPS，因此这些数值不能换算为无上限游戏帧率。

`perf_edits` 在玩家监测范围和 GI 体积以外放置、拆除遮挡墙，检查已发布阴影网格的实际变化及恢复，并检查近处新增光源是否获得阴影图。优化版还验证分片状态指纹与完整遮挡采集的指纹一致。角落与传送门固定镜头用于复核表面光照和反射。

给检查器增加 `--baseline-shaders /path/to/frozen/shaders` 可核对所有 Shader 输入保持一致。本轮最终实现只修改配套 Mod；尝试过的 GPU 提前退出通过像素对照，但整帧表现存在回退风险，已撤回。

捕获增加 `--fps-limit 120` 可测量实际吞吐，增加 `--flight-recording /path/to/profile.jfr` 可保存 JFR。比较时保持两版的 FPS 上限、窗口尺寸、视距和剖析设置相同。渲染线程的 CPU 和分配同时按实际帧数归一化，避免较高 FPS 自身增加每秒工作量造成误判。JFR 应使用流式工具读取，深栈展开为完整 JSON 会远大于原始记录。

自动镜头不会生成真实键鼠输入，捕获副本将 `inactivityFpsLimit` 设为 `minimized`。报告记录实际 FPS 上限与限帧原因，高帧率比较要求 `effective_fps_limit` 等于请求值且 `throttle_reason=NONE`。继承 AFK 设置会在无输入一分钟后降到 30 FPS，十分钟后降到 10 FPS，详见 [Minecraft 官方说明](https://www.minecraft.net/en-us/article/save-energy-with-the-frames-per-second-limiter-feature)。这一测试设置不写入正式游戏目录。

`perf_static` 还会在帧率采样结束后，预热并重复采集一个独立的 40³ 固定区域，包含完整方块、台阶、楼梯、栅栏、染色玻璃及玻璃板。该区域与四方块快照原点对齐。报告保存采集阶段的线程分配和 CPU 时间，以及完整体素、吸收数据和网格的 CRC；有同版固定区域标记时，比较器要求三个 CRC 和原点全部一致。只检查此项可增加 `--scene perf_static`。

## 本轮实测

2026-10-20 在上次已部署版本上继续优化。固定区域的对照结果如下：

| 单次 40³ 采集 | 修改前 | 修改后 | 减少 |
| --- | ---: | ---: | ---: |
| 线程临时分配 | 7.52 MiB | 2.26 MiB | 70% |
| 线程 CPU 时间 | 8.25 ms | 3.06 ms | 63% |

体素、玻璃吸收数据与完整网格的 CRC 均一致，四组几何探针的原始顶点 CRC 也通过。表格仅覆盖 CPU 采集阶段；场景发布仍需展开几何，不包含 GPU 上传或整帧耗时。所有 231 个 Shader 输入与本轮开始时一致，画质和运行参数保持原值。

六类原生场景与重复短测覆盖静止、移动、动态遮挡、内角光照、传送门和染色玻璃。最终 CPU 版本的远处墙体新增、拆除以及近处新光源映射均通过；近处映射约 0.46 秒。测试中整体帧率没有一致提升，因此本轮确认的收益是采集成本和冗余上传减少，不能据此宣称长时间游玩的帧率已稳定。

## 测量限制

2026-10-19 在本机 Apple M3、24 GB 内存上完成两组原生对照。其中独立封闭场景的渲染线程临时分配如下，三项均保持 64 光源和相同 GI 参数：

| 场景 | 修改前 MiB/s | 修改后 MiB/s | 减少 |
| --- | ---: | ---: | ---: |
| 静止 | 55.1 | 25.0 | 55% |
| 移动与转向 | 181.1 | 34.2 | 81% |
| 动态编辑 | 113.5 | 16.7 | 85% |

四组网格检查的临时分配减少约 76%–92%，顶点长度和字节 CRC 全部一致。两组原生测试均通过远处墙体新增、拆除及近处光源映射检查；近处光源约 0.5 秒获得阴影图。两幅相同镜头的角落与传送门对照保持原有光照和反射，平均 RGB 差异分别约为 0.43、1.15 个 8 位色阶，包含火焰、粒子、传送门和天空动画差异。

独立场景的渲染线程 CPU 时间没有一致下降：静止约 155→161 ms/s，移动约 194→189 ms/s，动态编辑约 153→169 ms/s。当前实测收益主要是降低临时分配和重复几何工作，不能据此宣称整机帧率提高。所有 231 个 Shader 输入文件与优化前哈希一致；132 个入口、108 项配置与 Java 21 目标构建通过检查。

减少临时分配有助于减轻垃圾回收与内存压力；结果仍取决于区块加载、可见几何、其他 Mod 和 GPU 负载。短时固定场景不能证明长时间探索的帧率始终稳定，也不能排除系统内存压力。修改配套 Mod 后需要完全重启客户端，F3 + R 只重载 Shader。
