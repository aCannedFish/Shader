# 02 · 着色器管线与程序类型

> 上一章讲了单段 GLSL 怎么写。这一章讲**这些代码什么时候被执行**，
> 以及 OptiFine 到底提供了哪些"插槽"让你往里塞代码。

---

## 1. 一帧里发生了什么

Minecraft 渲染一帧的过程（简化后）：

```
① 准备：计算摄像机矩阵、太阳位置、光照贴图、天气……

② 阴影通道（shadow.vsh / shadow.fsh）
   把场景从"太阳的视角"再渲染一遍，只记录深度 -> 一张深度贴图

③ 几何通道（gbuffers_*.vsh / gbuffers_*.fsh）
   从玩家视角渲染场景，分很多批次：
     不透明地形 -> 实体 -> 手持物品 -> 云 -> 天空 -> 半透明地形 -> 水 -> 天气
   每个批次可能用不同的着色器程序

④ 后处理通道（composite*.vsh / composite*.fsh）
   全屏处理：泛光、SSAO、景深、色调映射……

⑤ 输出（final.vsh / final.fsh）
   把结果写进帧缓冲，显示到屏幕
```

**②③④⑤ 就是你可以插手的所有地方**。每一处对应一对 `.vsh` / `.fsh` 文件，
文件名由 OptiFine 规定。

## 2. 缓冲区（G-Buffer）与 MRT

### 为什么要用缓冲区

一个像素的最终颜色依赖于很多东西：它是什么材质、表面朝哪、离摄像机多远、
有没有被遮挡……这些信息分散在不同时刻。

**做法**：把需要的中间结果写进几张纹理（渲染目标），后面的程序再读回来。

本项目用了 5 张：

| 缓冲区 | 格式 | 内容 |
|-------|------|------|
| `colortex0` | RGBA16F | 场景颜色（HDR） |
| `colortex1` | RGBA8 | `rg` 法线 xy、`b` 天空光、`a` 材质标记 |
| `colortex2` | RGBA8 | `r` 方块光、`g` 天空光、`b` 阴影系数 |
| `colortex3` | RGBA16F | 泛光：亮部提取结果 |
| `colortex4` | RGBA16F | 泛光：模糊结果 |

格式在 `settings.glsl` 里声明。注意**格式那一行必须包在块注释里**
（`RGBA16F` 是 OptiFine 语法、不是合法 GLSL，详见
[`07-调试排错与性能.md`](07-调试排错与性能.md)）：

```glsl
/*
const int colortex0Format = RGBA16F;
*/
const bool colortex0Clear = true;   // 这个不用注释，true 是合法 GLSL
```

### MRT：一次绘制写多张纹理

```glsl
// .fsh 里
gl_FragData[0] = vec4(color, alpha);   // -> colortex0
gl_FragData[1] = vec4(normalData);     // -> colortex1
gl_FragData[2] = vec4(lightData);      // -> colortex2
```

`gl_FragData[n]` 的第 n 个索引对应"这次绘制的第 n 个渲染目标"。
**一次绘制里写多张图，不产生额外开销**，这是 G-Buffer 方案能跑得动的原因。

> **新手常见错误**：以为 `gl_FragData[1]` 就是 `colortex1`。
> 它们只在"这次绘制绑定了 colortex0/1/2 作为目标"时才对应。
> 后处理阶段（`composite.fsh`）绑定的目标是 colortex3，
> 所以那里的 `gl_FragData[0]` 写的是 colortex3。

### `/* RENDERTARGETS: 3 */`

后处理程序需要显式声明写哪张图。这行**必须写在文件里**，
OptiFine 会扫描它（只能出现在注释里）：

```glsl
#version 120
/* RENDERTARGETS: 3 */      // 本次绘制写 colortex3

#include "/settings.glsl"
...
```

不写的话默认写 colortex0 —— 那会把刚渲染好的场景直接覆盖成黑屏。

## 3. gbuffers 程序类型速查

`gbuffers_` 前缀的程序负责"把场景画进 G-Buffer"。OptiFine 按渲染对象
把它们分成很多类，每一类你都可以单独接管：

| 程序 | 渲染对象 | 本项目的处理 |
|------|---------|------------|
| `gbuffers_basic` | 拴绳、调试线框 | 最简光照 |
| `gbuffers_line` | 区块边界的线框 | （未提供，回退到 basic） |
| `gbuffers_textured` | 不参与光照的粒子 | 只乘光照贴图 |
| `gbuffers_textured_lit` | 参与光照的粒子 | 完整光照 |
| `gbuffers_skybasic` | 渐变天空穹顶 | 直接输出，不做光照/雾 |
| `gbuffers_skytextured` | 带贴图的天空（末地等） | 采样贴图后直接输出 |
| `gbuffers_clouds` | 云 | 完整光照 + 淡雾 |
| `gbuffers_terrain` | **地形（核心）** | 完整光照 + 阴影 + 雾 |
| `gbuffers_damagedblock` | 方块裂纹 | 只输出材质 |
| `gbuffers_block` | 选中框 | 只输出材质 |
| `gbuffers_beaconbeam` | 信标光柱 | （未提供，回退） |
| `gbuffers_entities` | 生物、掉落物 | 完整光照 + 受伤闪红 |
| `gbuffers_hand` | 手持物品、手臂 | 完整光照 + 减弱的雾 |
| `gbuffers_weather` | 雨、雪 | 完整光照 + 阴天压暗 |
| `gbuffers_water` | 水（含所有半透明） | 完整光照 + 波浪 + 高光 |
| `gbuffers_spidereyes` | 蜘蛛/末影人的发光眼睛 | （未提供，回退） |

### 关于 `_a` 后缀

你可能注意到表里没有 `gbuffers_terrain_a`。**它不需要单独写**：

OptiFine 渲染半透明物体（玻璃、冰、水下的方块）时会寻找
`gbuffers_terrain_a`，找不到就回退到 `gbuffers_terrain`，
但把渲染状态改成：
- 开启 alpha 混合（而不是覆盖）
- `alphaTestRef` 设为 0（所以 `discard` 不会误伤）

**结果**：本项目的地形着色器同时处理不透明和半透明地形，
全靠 `alphaTestRef` 这个 uniform 自动适应。这也是为什么
`gbuffers_terrain.fsh` 里的 `if (albedo.a < alphaTestRef) discard;`
对两种情况都正确。

### 没有提供的程序会怎样

如果某个类型你没有写文件，OptiFine 会**回退**到 `gbuffers_basic`。
所以哪怕你只写 `gbuffers_terrain`，游戏也能跑 ——
只是其它物体走 basic 的简化逻辑。

**本项目的取舍**：提供了 15 个程序，覆盖所有常见物体，
让画面保持一致。想精简的话，删掉 `gbuffers_basic.vsh/.fsh` 之外的
任何一对，游戏依然能启动。

## 4. 后处理程序

`composite` / `composite1` / ... / `composite15` 是**编号的全屏通道**，
按编号从小到大依次执行。

```
composite   ->  composite1  ->  composite2  -> ... -> composite15  ->  final
```

每个通道渲染一个覆盖全屏的四边形，可以读任何 colortex，写任意 colortex
（由 `/* RENDERTARGETS: n */` 指定）。

本项目的用法：

| 程序 | 读 | 写 | 做什么 |
|------|----|----|-------|
| `composite` | colortex0 | colortex3 | 亮部提取 |
| `composite1` | colortex3 | colortex4 | 高斯模糊 |
| `final` | colortex0, colortex4 | 屏幕 | 色调映射 + gamma + 输出 |

### 执行顺序中隐藏的约束

**水面在 `composite` 之前就已经画完了吗？** 是的。
gbuffers 阶段全部结束后才进入 composite。所以 `final` 里读到的
colortex0 已经包含了水面。

这也是为什么**色调映射必须放在 `final` 而不是 gbuffers 阶段**：
如果地形在 gbuffers 里就被映射过、水面在它自己的程序里也被映射过，
两次映射的结果在接缝处对不上。统一放在最后一步，所有东西都被处理一次。

## 5. `#include` 与文件组织

OptiFine 不原生支持 `#include`，是它自己实现的预处理。
路径规则：**以 `shaders/` 目录为根**，前面加 `/`。

```glsl
#include "/settings.glsl"          // shaders/settings.glsl
#include "/lib/common.glsl"         // shaders/lib/common.glsl
```

### 为什么本项目的程序都这么短

因为公共逻辑全部下沉到了 `lib/`：

```
gbuffers_terrain.vsh (30 行)
    └── #include "/lib/vertex_transform.glsl"
            └── #include "/lib/space.glsl"
                    └── #include "/lib/uniforms.glsl"
                    └── #include "/lib/common.glsl"
```

调用链是**深度优先**的：先展开被包含的文件，再回到调用它的文件。

### 头文件保护是必须的

```glsl
#ifndef LIB_COMMON_GLSL     // 如果没定义过
#define LIB_COMMON_GLSL     // 定义它
... 文件内容 ...
#endif
```

没有这个保护，同一份代码被包含两次就会报"重复定义"。
例如 `gbuffers_terrain.fsh` 的包含链里 `common.glsl` 会被走到 3 次，
全靠这个保护去重。

## 6. 渲染顺序对画面的影响

**顺序决定了谁能覆盖谁**。本项目的顺序（OptiFine 默认）大致是：

```
天空 -> 地形（不透明）-> 实体 -> 手持物品 -> 云
     -> 地形（半透明）-> 水 -> 天气
```

两个实践结论：

1. **水能遮住沙子，沙子遮不住水**。因为水在后面画。
   想让水真的"透明"看到水底，靠的是 alpha 混合而不是顺序。

2. **屏幕空间效果不能跨顺序**。SSAO 要找"相邻像素的深度差"，
   但如果相邻像素一个来自地形、一个来自手持物品（两者在视图空间里
   隔了十万八千里），深度差会给出完全错误的遮蔽。

   解决办法是在后处理里用 `colortex1.a` 里的材质标记做判断：
   ```glsl
   float centerMat = texture2D(colortex1, uv).a;
   float neighborMat = texture2D(colortex1, uv + offset).a;
   if (abs(centerMat - neighborMat) > 0.1) { /* 跳过，不是同一种材质 */ }
   ```
   本项目已经在 `writeGBuffers()` 里把材质标记写好了，
   你扩展 SSAO 时直接用即可。

## 7. 设置界面不显示 / 是空的

如果你写了 `shaders.properties` 但游戏里的光影设置界面是空的，
检查**子页面必须写成方括号形式**：

```properties
screen = <empty> [SHADOWS] [LIGHTING] [POST]
screen.SHADOWS = ENABLE_SHADOWS SHADOW_SOFTNESS
```

写成 `screen = SHADOWS LIGHTING POST`（不加方括号）不会报错，
但 OptiFine 会把 `SHADOWS` 当成一个**选项名**去找，找不到就在日志里刷：

```
[Shaders] Invalid option: SHADOWS, key: screen
```

界面于是整个是空的。

## 8. 亲手验证：打印程序的执行顺序

想确认哪个程序先跑？改一下颜色就行：

```glsl
// gbuffers_terrain.fsh 的 main() 末尾，临时加上：
gl_FragData[0] = vec4(1.0, 0.0, 0.0, 1.0);   // 地形全红
```

```glsl
// gbuffers_water.fsh 的 main() 末尾，临时加上：
gl_FragData[0] = vec4(0.0, 0.0, 1.0, 1.0);   // 水全蓝
```

进游戏（`F3 + R` 重载）你会看到：地形是红的、水是蓝的 ——
说明两者确实走了不同的程序。如果把水的那行删掉，
水会变成红色 —— 说明它回退到了地形的程序。

**这是理解"程序类型"最快的方法**，比读文档快十倍。
